# Understanding and Implementing a Tokenizer

If you've read the previous article, [What Are the Main Components of a Complete LLM?](v0_01.md), the natural place to start is the first step: the Tokenizer.

As discussed in the previous article, the Tokenizer's main job is to split continuous text into the smallest units the model can process, commonly called **Tokens**, and convert them into numeric identifiers, commonly called **Token IDs**.

A Token can be a visible character ("A"), an invisible character ("`&#8203;`"), a word ("movement"), a phrase ("kind of"), part of a word or phrase ("ment"), or even an emoji (:rocket:). How Tokens are defined depends on the LLM's implementation. Token IDs are easier to understand: each defined Token is assigned a numeric ID.

Clearly, a Tokenizer takes the user's original input (Input) and produces a sequence of Tokens and their corresponding Token IDs.

The central question is: how do we turn Input into a sequence of Tokens and Token IDs?

If you've used search engines for years, one approach that may come to mind is to build a comprehensive list of Tokens, assign each one an ID, and then segment Input using a traditional search-engine tokenization algorithm.

Indeed, this is a natural approach, and it has practical uses.

But it also raises a series of questions:

- Where would we find such a comprehensive Token list?
- Human languages keep evolving. How would we maintain the list?
- What happens if Input contains a Token that isn't on the list?
- Would segmenting text using that list necessarily produce good Tokens?
- If I only want to train a domain-specific model, why do I need a comprehensive list?
- Some Tokens are special markers in my domain. Could a general-purpose list cover those too?

Let's work through these questions. Once we resolve them, the approach to implementing a Tokenizer will become much clearer.

## Tokenizer Trainer

### Analyzing the Problem

Looking more closely, we can see that all these questions stem from the idea of a "comprehensive Token list." As long as we insist on such a list, these problems may be difficult to solve effectively.

What if we change our perspective? Do we really need a comprehensive Token list? The answer is no.

A Token list only needs to meet two requirements to address the problems above.

First, any input must be representable using Tokens already in the list, without losing information.

Second, for the training corpus, that is the corpus used by the Trainer, we should find a suitable set of Tokens so that the Tokenizer's segmentation results (hereafter simply called "tokenization results") make training more efficient.

Let's briefly explain this. In [What Are the Main Components of a Complete LLM?](v0_01.md), we said that the Trainer feeds large amounts of data into the model during training. Here, that "data" is what we call the "training corpus." During training, the model only encounters the training corpus, so tokenization that works efficiently for that corpus can be very helpful. That is our second requirement. Later, when the model is in its working stage (the Generator, which produces text from user input), we cannot control what users enter. The first requirement ensures that none of that input information is lost.

So the next question is: how can we find a Token list that meets both requirements?

Think about it for a moment. It isn't too difficult.

To meet the first requirement, if we use UTF-8 encoding, we only need to include all 256 possible basic byte values, represented as Tokens, in our list.

To meet the second requirement, we generate Tokens from the training corpus, aiming for a list that improves training efficiency. And that is the core responsibility of the **Tokenizer Trainer**.

There is an important distinction in terminology here. The Tokenizer Trainer extracts a Token list from the training corpus that provides full coverage and is suitable for training. It is not the same as the **Trainer** described as an LLM component in the previous article, the one that trains the model itself. Think of the Tokenizer Trainer as a submodule of the Tokenizer, responsible for generating a fully covering, training-friendly Token list from the corpus.

Now another question arises: full coverage is straightforward, as we've just discussed. But how do we generate a Token list from the training corpus? And how can we make that list improve training efficiency?

### The BPE Algorithm

There are several established approaches in the industry, including Byte Pair Encoding (BPE), WordPiece, and the Unigram Language Model. Personally, I find BPE's basic idea simple and clear. It has also been used in well-known products such as ChatGPT, so I chose to implement BPE for the V0 Tokenizer in this project. See [/v0/tokenizer/bpe_trainer.cpp](../v0/tokenizer/bpe_trainer.cpp) for the implementation.

Let's go through the principles behind BPE. I hope this explanation helps you understand the implementation, and you're welcome to look for bugs in [my code](../v0/tokenizer/bpe_trainer.cpp).

**Step 1.** Define three variables: *t*, the maximum number of iterations; *n*, the desired number of Tokens; and *tokens*, the resulting Token set.

**Step 2.** Define a base Token set. The simplest choice is the set of 256 basic byte values mentioned earlier, which provides full coverage. Add them to *tokens*.

**Step 3.** Repeat the algorithm. In each iteration, tokenize the training corpus using the current *tokens*, count adjacent Token pairs, select the *m* most frequent pairs, concatenate each pair into a new Token, and add the new Tokens to *tokens*.

**Step 4.** Stop when the algorithm has completed *t* iterations or *tokens* contains at least *n* Tokens. The resulting *tokens* set is the output.

Note that Step 3 describes **my own variant**. Classic BPE merges only the single most frequent adjacent Token pair in each iteration.

### An Example of BPE

Suppose the training corpus contains only four characters: "a", "b", "c", and "d". So, these four characters are enough for full coverage in this simplified example. Let *t* = 2, *n* = 14, and *m* = (*n* - 4) / *t* = 5. Our training corpus is `ababccddabdaccba`.

| Iteration | Current *tokens* | Tokenized corpus | Adjacent Token pair frequencies | New Tokens from merging | Updated *tokens* |
| --- | --- | --- | --- | --- | --- |
| 0 | a, b, c, d | a, b, a, b, c, c, d, d, a, b, d, a, c, c, b, a | N(a, b) = 3 <br /> N(b, a) = 2 <br /> N(c, c) = 2 <br /> N(d, a) = 2 <br /> N(b, c) = 1 <br /> N(c, d) = 1 <br /> N(d, d) = 1 <br /> N(b, d) = 1 <br /> N(a, c) = 1 <br /> N(c, b) = 1 | ab, ba, cc, da, bc | a, b, c, d, ab, ba, cc, da, bc |
| 1 | a, b, c, d, ab, ba, cc, da, bc | ab, ab, cc, d, da, b, da, cc, ba | N(ab, ab) = 1 <br /> N(ab, cc) = 1 <br /> N(cc, d) = 1 <br /> N(d, da) = 1 <br /> N(da, b) = 1 <br /> N(b, da) = 1 <br /> N(da, cc) = 1 <br /> N(cc, ba) = 1 | abab, abcc, ccd, dda, dab | a, b, c, d, ab, ba, cc, da, bc, abab, abcc, ccd, dda, dab |

When candidate Token pairs have the same frequency, this example selects them in the order shown in the table.

At this point, the algorithm has completed *t* = 2 iterations, and the Token count has reached *n* = 14. The stopping conditions are met.

The final *tokens* set is:

`{ a, b, c, d, ab, ba, cc, da, bc, abab, abcc, ccd, dda, dab }`

### Summarizing BPE

Does the result of BPE meet our two requirements? The first requirement is clearly satisfied: in the full implementation, Step 2 already adds all 256 basic byte values to *tokens*.

What about the second requirement? The Token set is generated from the training corpus, so that part is fine. But does it actually improve training efficiency?

First, we need to decide what "improving training efficiency" means. The criterion is a matter of perspective, and different reasonable definitions are possible. If we define it as **reducing the number of Tokens needed to represent the training corpus**, then BPE can help achieve that goal. The reason is straightforward: in Step 3, it merges frequently occurring adjacent Token pairs.

### The Complete Tokenizer Trainer Implementation

How do we assign Token IDs to the generated Tokens? My implementation is simple: sort all the generated Tokens, assign a Base ID to the first Token, and give each subsequent Token an ID one greater than the previous one. This produces a contiguous range of integer Token IDs. Why is that useful? I'll leave that as a little teaser. The benefit will become clear when we discuss Embedding later.

We can also add special-marker Tokens to the algorithm and assign their Token IDs within contiguous ranges, meeting the needs of domains that use special markers.

In my V0 implementation, the Tokenizer Trainer is a standalone executable. Before model training, I run it on the entire training corpus to produce a complete Token list that can be saved to a file. That saved Token list is then used consistently by all subsequent operations. See [/v0/cmd/tokenizer.cpp](../v0/cmd/tokenizer.cpp).

## Tokenizer Encoder

There's one problem we glossed over earlier: Step 3 of BPE says to tokenize the training corpus using *tokens*.

That requires an actual tokenization algorithm. In other words, we need a way for the Tokenizer to take any input including training data and user input, and output a sequence of Tokens. We call this the **Tokenizer Encoder**.

Although we passed over it quickly, it is important. Fortunately, the basic idea is fairly simple. We can use a classic greedy tokenization algorithm based on a state machine, similar to those used in search engines.

The algorithm scans the input string from beginning to end. At each position, it finds the **longest string that exists in *tokens*** and emits that string as the next Token.

See [/v0/tokenizer/greedy_encoder.cpp](../v0/tokenizer/greedy_encoder.cpp) for the implementation.

Clearly, a Tokenizer Trainer based on the BPE approach described above needs to invoke the Tokenizer Encoder multiple times.

Again, using a greedy Tokenizer Encoder inside this BPE-inspired algorithm is part of my variant. The Encoder used by classic BPE works somewhat differently, but I won't go into those details here.

## Problems I Encountered During Implementation

### The Case-Sensitivity Dilemma

Uppercase and lowercase letters gave me quite a headache during implementation.

On one hand, I thought capitalization at the beginning of a sentence was merely a rule. Why not convert everything to lowercase? When generating text, I could simply capitalize the Token following a period Token. That would avoid having multiple Tokens for the same word and might make training and generation clearer.

On the other hand, capitalization can change a word's meaning. Consider the classic example of "apple" and "Apple": one refers to a fruit, while the other could be that fruit at the beginning of a sentence or a technology company. There are many more examples. Perhaps the most striking is "us" versus "US", whose meanings are completely different.

After wrestling with this for a while, I thought: why not let the model handle it? A sufficiently capable model should be able to learn capitalization rules and distinguish meanings from context.

If that works, I wouldn't need to handle case conversion in the Tokenizer, which would simplify the implementation. Still, I didn't want to jump to conclusions, so I decided to look at how the industry handles this problem.

I found a website called [Tiktokenizer](https://tiktokenizer.vercel.app/). Using the gpt-4o model option, I entered `this` and `This` and checked their Token IDs. They were different.

That suggested my earlier idea might be reasonable. So I decided not to normalize case: I would preserve the capitalization in the training corpus and treat differently capitalized forms of the same word as different Tokens.

Of course, models differ in architecture and complexity. This single observation cannot prove that every model can learn all capitalization rules correctly, or that preserving case is always better than converting everything to lowercase.

### The Curse of Spaces

`I love AI, AI...`

Once I'd settled the case-sensitivity issue, spaces started giving me trouble.

My stubbornness was at work again. I thought spaces were just another rule. What if I simply added a space after every Token when generating text? Then spaces wouldn't need to be Tokens, and I could save a large number of Tokens during tokenization.

But a problem appeared immediately. When I tested the sentence above, a little expression of my affection for AI, I found that without spaces acting as separators, BPE merged Tokens from neighboring words together.

I ended up with Tokens like `AI,AI`, `Il`, `Ilove`, `eA`, and `veAI`. That was ridiculous! These Tokens made no linguistic sense in the context of what I wanted to build, and they could interfere with training.

Apparently, ignoring spaces wasn't going to work. So how should I handle them? I asked ChatGPT and got several possible approaches. One common approach is to allow spaces to merge with what follows them, but not with what precedes them. For example, ` love` is allowed, while `love ` is not.

I checked [Tiktokenizer](https://tiktokenizer.vercel.app/) again. With the gpt-4o model option, ` this` was encoded as one Token, while `this ` was encoded as two Tokens. This showed that such a space-handling approach was still used by a popular model.

That approach certainly works. But it raised another question. Established LLM products have enormous training corpora. Both `this` and ` this` are common enough to be well represented in their training data, so they don't need to worry much about the distinction.

I'm just one person building a Mini-GPT on my own computer. I don't have nearly as much training data, computing power, or money. So if I want my small model to learn patterns quickly, **Token reuse matters a great deal**.

I brought this point up with ChatGPT, and after several rounds of discussion, we reached a general agreement.

So I decided to **treat spaces as independent Tokens**.

That decision turned out to be enormously helpful. Here's a little preview: when I finished testing my V0 implementation, the model still couldn't produce coherent sentences, but the way it handled spaces helped me recognize that V0 was working. Why? I'll save that story for the final article in the V0 series.

There was one more problem to solve: preventing merges across word boundaries. Once spaces were independent Tokens, this became relatively straightforward. I defined a rule: digits can merge with digits, letters can merge with letters, and other combinations cannot merge.

You can find the implementation of this rule in the `can_be_merged` method in [/v0/tokenizer/base.cpp](../v0/tokenizer/base.cpp).

With spaces and merging rules handled, I tested that little expression of affection again. This time, the results looked much better:

`A`, `AI`, `lo`, `love`, `ov`, `ve`, ...

### Handling Tokens at the End of Input

Finally, a quick note about a bug I encountered. In the greedy Tokenizer Encoder, it's easy to overlook a valid Token at the very end of the input. Once the scanning loop reaches the end, it may exit without emitting that final Token. I fell into this trap myself, and I hope you can avoid making the same mistake.

## Summary

That's everything for this article. The main focus was how to implement a Tokenizer that converts input into a sequence of Tokens, laying the foundation for model training and text generation.

A Tokenizer consists of two parts: the **Tokenizer Trainer** and the **Tokenizer Encoder**.

The Tokenizer Trainer extracts Tokens from the training corpus. It needs to provide full coverage and produce tokenization results that are efficient for training. In this section, we focused on the principles and implementation of BPE.

The Tokenizer Encoder uses an existing Token list to split input into a sequence of Tokens for subsequent processing. Its greedy, state-machine-based implementation deserves particular attention.

In the next article, we'll move on to **Embedding**. Things may get a little more challenging, but that's all right. We'll learn and make progress together.
