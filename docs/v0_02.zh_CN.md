# Tokenizer 的原理与实现

相信你已经阅读了上一篇“[一个完整的 LLM 由哪些部分组成](v0_01.zh_CN.md)”，那么，很自然地，我们从第一步 Tokenizer 开始。

如上篇所述，Tokenizer 的核心功能是将连续的文本切分成模型可以处理的最小单元，就是我们常说的 Token，并将它们转换为数字 ID 的表示，就是我们常说的 Token ID。

Token 可以是一个可见字符（“A”），一个不可见字符（“`&#8203;`”），一个词语（“羽毛”），一个词组（“有羽毛的”），一个词语或词组分拆成的一部分（“有”，“羽”，“的”），或者是一个 emoji 表情（:rocket:）。具体如何定义每个 Token，取决于 LLM 的实现策略。Token ID 理解起来比较简单，就是给每个定义好的 Token 指派一个数字 ID。

显然，Tokenizer 的输入就是用户对 LLM 的原始输入（Input），输出就是根据这个 Input 转换成的一系列 Token 和 Token ID。

这里的核心问题就是，如何把 Input 转换成一系列的 Token 和 Token ID。

多年使用搜索引擎的你，最容易想到的实现方法应该是，定义一个大而全的 Token 列表，每个 Token 指派一个 ID，然后再根据搜索引擎经典的分词算法来分割 Input。

没错，这确实是一个很自然，也有实际应用价值的办法。

但一系列问题也随之而来：
- 哪儿来找这个大而全的 Token 列表？
- 人类的语言随时间的推移不断进化，这个大而全的 Token 列表要如何维护？
- 假如我的 Input 中出现一个列表中不存在的 Token，该如何处理呢？
- 按照大而全的 Token 列表分割出来的 Token 就一定好吗？
- 我只想训练特定领域的模型，我为什么非要大而全的 Token 列表呢？
- 有些 Token 在我的领域中属于特殊标记符号，所谓大而全的 Token 列表，能够涵盖这些吗？

下面我们就来解决这些问题。这些问题解决了之后，Tokenizer 的实现思路也就清晰了。

## Tokenizer Trainer

### 问题分析

仔细分析上面的问题，我们会发现，所有问题都出在这个“大而全的 Token 列表”上。只要存在这么一个“大而全的 Token 列表”，恐怕这些问题就无法有效地解决。

不妨换个思路，这个“大而全的 Token 列表”，是必须的吗？答案是否定的。

一个 Token 列表，只要满足两个条件，就可以解决上面所有的问题。

第一个条件，任何输入都能被分解成列表中的已有 Token，不会丢失信息。

第二个条件，针对训练语料，即 Trainer 所用到的语料，能够找到一套比较合适的 Token，使 Tokenizer 的分词结果（即上文所说的转换出一系列 Token 的结果，这里用“分词结果”简略指代，下文同）在训练过程中效率更高。

这里我们简要解释一下。在上一篇“[一个完整的 LLM 由哪些部分组成](v0_01.zh_CN.md)”里说过：Trainer 负责在模型训练阶段，把海量的数据喂给模型。这里说的“数据”，和我们刚才所说的“训练语料”是相同的意思。模型在训练过程中，只会接触到训练语料，因此，对训练语料高效的分词结果，对训练模型很有帮助，这就是我们所说的第二个条件。而到了模型的工作（即 Generator，根据用户输入生成文本的）阶段，由于用户输入难以控制，满足第一个条件就可以保证没有丢失用户输入的任何信息。

那么，接下来的一个问题就是，如何找到一个 Token 列表可以同时满足以上两个条件呢？

其实想想，并不难。

如果想满足第一个条件，使用 UTF-8 字符编码，那么只需要让所有的 256 种基础字节字符，都出现在 Token 列表当中。

如果想满足第二个条件，那么我们就从训练语料集合中生成 Token 列表，并保证该列表在训练过程能够提高效率。而这，就是 Tokenizer Trainer 的核心功能。

这里必须指出一个关键的名称区别，这里所说的 Tokenizer Trainer，是在训练语料集合中，提取一个全覆盖且训练友好的 Token 列表。它和我们上一篇“[一个完整的 LLM 由哪些部分组成](v0_01.zh_CN.md)”里面说到的 LLM 组成部分的 Trainer（即前文说到的模型训练阶段的那个 Trainer）不是一回事，Tokenizer Trainer 可以认为是 Tokenizer 中的一个子模块，专门负责基于训练语料，生成全覆盖，且能帮助训练过程提高效率的 Token 列表。

那么，问题就又来了：全覆盖是简单，刚才已经说过了。但如何基于训练语料生成 Token 列表呢？怎么生成才可以做到在训练过程中提高效率呢？

### BPE 算法

业界对这个问题，有许多成熟的办法可以选择。比较常见是 Byte Pair Encoding（BPE），WordPiece 和 Unigram Language Model。我个人觉得 BPE 的思路简单清晰，也曾经被 ChatGPT 这种经典产品所使用，因此，我就实现了 BPE 作为本项目的 V0 版本的 Tokenizer。具体实现参见 [/v0/tokenizer/bpe_trainer.cpp](../v0/tokenizer/bpe_trainer.cpp)。

下面介绍一下 BPE 的算法原理。希望大家可以参照原理来理解实现，也欢迎帮我在[实现代码](../v0/tokenizer/bpe_trainer.cpp)中找找 bug。

第一步，定义三个变量，算法运行的最大次数 *t*，期望提取的 Token 数量 *n*，以及结果 Token 列表集合 *tokens*。

第二步，定义一个基础 Token 集合。最简单直观的基础 Token 集就是上文说的，可以做到全覆盖的 256 种基础字节字符集。将它们加入 *tokens* 中。

第三步，重复运行算法，每次将训练语料根据 *tokens* 分词，统计出频率最高的 *m* 对相邻 Token，把它们合并成新的 Token 并加入 *tokens* 中。

第四步，直到算法已经运行 *t* 次或者 *tokens* 中已经有大于等于 *n* 个 Token，退出。此时 *tokens* 里面的所有 Token 就是 BPE 算法的输出了。

这里需要指出，上面第三步是鄙人实现的变体，经典 BPE 算法每次只会合并频率最高的一对相邻 Token。

### BPE 算法举例

假设训练集中只有 “a”，“b”，“c”，“d” 四个字符，即四个字符就可以做到全覆盖。我们选定 *t* = 2，*n* = 14，*m* = (*n* - 4)/*t* = 5，训练语料是 "ababccddabdaccba"，则有：

| 轮次 | 当前 *tokens* | 语料分词结果 | 相邻 Token 对频率 | 合并产生的新 Token | 更新之后的 *tokens* |
| --- | --- | --- | --- | --- | --- |
| 0 | a, b, c, d | a, b, a, b, c, c, d, d, a, b, d, a, c, c, b, a | N(a, b) = 3 <br /> N(b, a) = 2 <br /> N(c, c) = 2 <br /> N(d, a) = 2 <br /> N(b, c) = 1 <br /> N(c, d) = 1 <br /> N(d, d) = 1 <br /> N(b, d) = 1 <br /> N(a, c) = 1 <br /> N(c, b) = 1 | ab, ba, cc, da, bc | a, b, c, d, ab, ba, cc, da, bc |
| 1 | a, b, c, d, ab, ba, cc, da, bc | ab, ab, cc, d, da, b, da, cc, ba | N(ab, ab) = 1 <br /> N(ab, cc) = 1 <br /> N(cc, d) = 1 <br /> N(d, da) = 1 <br /> N(da, b) = 1 <br /> N(b, da) = 1 <br /> N(da, cc) = 1 <br /> N(cc, ba) = 1 | abab, abcc, ccd, dda, dab | a, b, c, d, ab, ba, cc, da, bc, abab, abcc, ccd, dda, dab |

对于频率相同的候选 Token 对，本例按照表格中列出的顺序选择。

算法运行至此时，*t* = 2 且 *n* = 14，满足循环结束条件，退出。

最终的 *tokens* = { a, b, c, d, ab, ba, cc, da, bc, abab, abcc, ccd, dda, dab }

### BPE 算法总结

BPE 算法的结果是否满足前面说的两个条件呢？第一个条件很显然满足了，因为上面所说的第二步，已经把 256 种基础字节字符集加入 Tokens 当中了。

第二个条件呢？这个集合是基于训练语料生成的，这个也没有问题。但它是否能在训练过程中提高效率呢？

那我们就先看看什么叫做“在训练过程中提高效率”。其实，“在训练过程中提高效率的标准”是一个观点，观点嘛，当然是见仁见智的，只要合理就好。如果我们定义这个标准，是在训练过程中，尽量减少训练语料对应的 Token 数量，那么，BPE 算法确实可以达到这个标准。原因也十分明显，因为第三步中，它对出现频率最高的相邻 Token 对做了合并。

### Tokenizer Trainer 的完整实现

那么，对这些生成的 Token 指定 Token ID 呢？我的实现比较简单，给所有生成的 Token 排序，给序列中的第一个 Token 一个 Base ID，后面的每个 Token 的 ID 都是前一个 Token 的 ID 加 1。这样，所有 Token ID 放在一起，会形成连续的整数值集合。这样指定 ID 的好处是什么呢？这里先卖个关子，后面我们讨论 Embedding 的时候，就会自然地体现出来。 

此外，我们还可以在算法中加入定义一些特殊标记符号的 Token，并且给这些 Token 指定连续区间的 Token ID，以满足上文中提到的，某些领域中可能用到特殊标记符号的需求。

Tokenizer Trainer 在鄙人的 V0 实现中作为一个单独的可运行程序存在。训练之前，先对所有训练语料运行这个程序，得到可以保存的完整的 Token 列表。这个保存为文件的 Token 列表会被统一用于后续的所有操作当中。具体实现请参见 [/v0/cmd/tokenizer.cpp](../v0/cmd/tokenizer.cpp)。

## Tokenizer Encoder

上文其实还有一个被我们一笔带过的问题：BPE 算法的第三步，根据 *tokens* 分词。

这就涉及到分词的实现，其实也就是 Tokenizer 针对所有的输入（包括训练语料和用户输入），最终输出一系列 Token 的实现。我们把这个叫做 Tokenizer Encoder。

尽管上文一笔带过了，但它很重要。不过，虽然重要，却比较简单。我们可以把搜索引擎里面经典的，基于状态机的贪心分词算法用在这里。

算法思想就是从前到后扫描输入字符串（可以是训练语料也可以是用户输入），每次找到在 *tokens* 里面存在的最长的字符串作为分割出来的 Token 即可。

具体实现参见 [/v0/tokenizer/greedy_encoder.cpp](../v0/tokenizer/greedy_encoder.cpp)。

很显然，如果是基于 BPE 算法实现的 Tokenizer Trainer，需要多次调用 Tokenizer Encoder。

这里同样需要指出，上文的 BPE 算法调用基于贪心分词算法的 Tokenizer Encoder 也是一个变体，经典 BPE 算法的 Tokenizer Encoder 会略有不同，这里不过多展开。

## 实现过程中遇到的问题

### 大小写的困惑

实现过程中，大小写的问题一直困扰着我。

一方面，我觉得句首单词的大写不过是一个规则而已，可以把它转成小写。等到后面生成文本的时候，句号 Token 的下一个 Token 转成大写就好，免去了同一个单词多个 Token 的麻烦，后面训练和生成文本应该也会更加清晰。

另一方面，有的词的大小写表示两个意思。比如最经典的“apple”和“Apple”，前者只是一种水果，后者可以表示这种水果放在句首的写法，也可以表示某科技公司。再想想，其实还有很多例子，其中最离谱的是“us”和“US”，涵义相去甚远。

一番折磨后，我想，既然这么复杂，不妨交给模型来做。模型应该是足够强大的，可以训练出句首大写的规则，也可以区分出不同词的大小写在上下文中的意思。

如果是这样的话，那应该可以不用处理大小写 Token 的问题，实现就会比较简单。但我不敢妄下结论，就想着，要不找一找，看看业界如何处理这个问题。

于是我找到了一个网站叫做 [Tiktokenizer](https://tiktokenizer.vercel.app/)，在 gpt-4o 模型下，输入了 this 和 This 查看它们的 Token ID，结果是不一样的。

这说明，我之前的想法也许是对的。因此我就放心大胆地做了决定，不处理 Token 大小写的问题，保持训练语料的大小写，同一个词的大小写视为不同的 Token。

但这里需要指出，由于不同模型的结构和复杂性不同，不能单凭这一点就证明所有模型一定能够正确理解所有大小写规则，也不能证明保留大小写必然比统一小写更好。

### 空格的魔咒

"I love AI, AI..."

大小写的问题敲定了方案之后，空格又来烦我了。

还是之前的执拗心态作祟，想着空格这个东西，其实也是一个规则而已。生成文本的时候，每个 Token 输出之后，加一个空格输出，这样做，空格可以不作为 Token，就能在分词的时候省掉大量的 Token。

但问题立刻就来了，当我用上面的这个表达我喜爱之情的句子做测试的时候，发现没有空格作为 Token 分隔，前后两个 Token 就被 BPE 算法给合并到一起了。

居然出现了这种 Token：“AI,AI”，“Il”，"Ilove"，"eA"，“veAI”。这就太离谱了。这样的 Token 不仅语言上没有任何意义，还会干扰模型的训练。

不识别空格，看起来是不行的。那么如何识别空格呢？我问了 ChatGPT，得到了多种方法。比如最经典的就是空格可以向后合并，但不能向前合并，比如“ love”是可以的，“love ”就不行。

我又用 [Tiktokenizer](https://tiktokenizer.vercel.app/) 验证了一下，发现 gpt-4o 模型下，“ this”被识别为一个 Token，而“this ” 就是两个 Token，这说明这个经典的方法依然被流行模型所使用。 

这当然可以，可是又有一个问题来了。业界已经成型产品的 LLM 肯定行，因为它们的语料十分丰富，“this”和“ this”都十分常见，都会被充分训练，所以不必在乎。

但我是独身一人实现一个 Mini-GPT，而且是用我的个人电脑。我没有那么多的语料，也没有那么多的训练资源和金钱。因此，想让小模型快速学习到规律，Token 能够复用就很重要。

我把这个观点抛给了 ChatGPT，几轮讨论下来，基本能够达成一致。

因此，我决定把空格当成独立的 Token 来处理。

这个决定，给我带来了巨大的好处。不妨提前剧透一下，正是因为这样的处理，我在完成 V0 代码测试的时候，虽然它说不成人话，但我可以判断 V0 是成功的。为什么呢？这里还是先卖个关子，在 V0 的最后一篇收官文章里，我会详细说明。

最后，还要解决一个不能跨词合并的问题。既然空格是独立的 Token 了，那就比较简单了。我定义了一个规则，数字和数字可以合并，字母和字母可以合并，其他的都不能合并。

这个规则的实现可以参见 [/v0/tokenizer/base.cpp](../v0/tokenizer/base.cpp) 中的 can_be_merged 方法。

有了空格处理和合并的规则，再对这个表达我喜爱之情的句子做测试的时候，结果就十分漂亮了。

“A”，“AI”，“lo”，“love”，“ov”，“ve”，……

### 处理输入尾端 Token

最后简单介绍一个实现的 bug，在 Tokenizer Encoder 的贪心分词过程中，比较容易忽略的是末尾的合法 Token。因为循环已经走到末尾，很容易直接跳出而漏掉末尾的 Token。我在这里踩了坑，希望大家不要犯和我一样的错误。

## 总结

以上就是本篇的全部内容了。重点就是如何实现一个 Tokenizer，通过这个 Tokenizer，我们可以把输入变成一系列的 Token，为我们后续的训练和文本生成打下坚实的基础。

Tokenizer 分为 Tokenizer Trainer 和 Tokenizer Encoder 两个部分。

Tokenizer Trainer 帮助我们从训练语料中提取 Token，需要满足全覆盖，以及分词结果在训练过程中效率高这两个条件。在这部分，我们主要介绍了 BPE 算法的原理和实现。

Tokenizer Encoder 根据已有的 Token 列表，将输入分成一系列的 Token 供后续使用。基于状态机的贪心分词算法的实现需要重点关注。
